# Command Code 구현 위임

## 역할과 실행 설정

- 메인 모델은 기획·계획·설계·중요 판단을 담당하고 목적·요구사항·수정 범위·완료 기준과 검증·테스트 전략을 정한다. 사용자가 선택한 메인 모델을 유지한다.
- 코드 구현·작성·수정은 단순·복잡 여부와 관계없이 원칙적으로 작업자에게 위임한다. 테스트 작성·수정·실행, 린트·타입 검사·빌드, 실패 디버깅과 개발 중 검증·수정·재검증도 작업자가 담당한다. 테스트 실행만 요청된 작업에도 적용한다.
- 메인 모델은 기획·설계에 필요한 코드·컨텍스트 열람, 작업 분할·조율, 최종 인수 검증·리뷰를 수행한다. 작은 작업이나 간단한 수정이라는 이유로 구현을 직접 맡지 않는다. 작업자의 전체 검사를 상시 중복 실행하거나 발견한 결함을 직접 고치지 않되, 최종 수락 판단에 필요한 결정적 확인 실행은 직접 할 수 있다. 사용자가 직접 수행을 요청하거나 역할 변경을 승인한 경우에만 예외로 한다.
- 복잡한 작업은 메인 모델이 설계를 확정한 뒤 범위가 명확한 여러 작업으로 나눠 순차 또는 병렬로 위임한다. 작업자는 재량으로 해석할 수 없는 중요한 설계 모호성을 만나면 임의로 결정하지 않고 근거와 선택지를 제시해 메인 모델에 에스컬레이션하고, 메인 모델이 결정하면 그 결정에 따라 계속 진행한다.
- 작업자의 모델·추론 강도·권한 설정은 다음 우선순위로 정한다.
  1. 이번 요청에서 사용자가 명시한 값.
  2. 해당 작업에 적용되는 개인·프로젝트 지침.
  3. 기존 Command Code 설정(설정 파일·세션 기본값).
- 항목별로 지정된 값만 플래그로 넘긴다. 지정되지 않은 항목은 해당 플래그(`--model`, `--effort`)를 생략해 CLI 기본값을 따르게 한다. 예를 들어 모델만 지정되고 추론 강도는 언급되지 않았으면 `--model`만 붙이고 `--effort`는 붙이지 않아 기본 추론 강도를 유지한다.
- 호스트 메인 모델을 작업자 모델로 추론하지 않는다. 모델·추론 강도를 임의로 만들어내지 않고, 기존 지속 설정을 조용히 변경하지 않는다.
- 비대화형 실행은 `cmd -p --output-format json`에 작업에 맞는 `--max-turns`를 붙여 호출한다. 위 우선순위에서 정해진 모델·추론 강도·권한 플래그만 추가한다.
- `--yolo`는 사용자가 이미 명시적으로 권한을 부여한 경우에만 사용한다. 이미 허용된 설정은 매 실행마다 다시 묻지 않는다. 그 외에는 CLI의 권한 설정을 그대로 따르며, 비대화형 권한 때문에 실행이 막히면 우회하지 않고 `BLOCKED`로 보고한다.
- Node.js 22 이상에서 실행한다. 디렉터리별 설정이 Node 20 등을 선택하면 설치된 Node 22 이상 런타임의 bin 디렉터리를 해당 호출의 PATH 앞에 지정한다.
- 병렬 편집 또는 사용자 변경과 충돌할 수 있으면 별도 worktree로 격리한다. 메인 모델은 작업자가 편집 중인 파일을 동시에 수정하지 않는다.

## 작업자에게 전달할 내용

Command Code CLI를 독립된 컨텍스트와 실행 루프를 가진 외부 서브에이전트로 사용한다. Codex 내장 서브에이전트처럼 대화나 상태가 자동 공유된다고 가정하지 않는다.

기능 하나의 구현·테스트·수정을 함께 맡기는 것을 기본으로 한다. 함수 하나나 명령 하나마다 새 호출을 만들지 않는다. 독립적으로 완료·검증할 수 있는 경계나 컨텍스트 크기 때문에 필요한 경우에만 작업을 분할한다.

외부 CLI는 현재 대화나 Codex 지침을 자동으로 공유하지 않는다. 다음을 명시적으로 전달한다.

- 작업 목적과 기대 동작, 수정 허용 범위와 제외 범위.
- 적용할 프로젝트 지침과 필요한 파일·컨텍스트. 비밀정보는 프롬프트에 넣지 않는다.
- 완료 기준과 변경에 맞는 테스트·타입 검사·린트 등 검증 방법.
- 아래 자체 완료 절차와 최종 인계 형식. 이 위임 지침을 재귀 적용해 다른 작업자를 호출하지 않고 직접 구현·검증하도록 명시한다. 작업자는 메인 모델에만 결과를 인계하고 스스로 추가 위임하지 않는다.
- 재량으로 해석할 수 없는 중요한 설계 모호성은 임의로 결정하지 않고, 근거와 선택지를 제시해 메인 모델의 결정을 요청하도록 명시한다.

위 내용을 작업별 지시서 파일 하나로 정리해 `cmd -p`의 표준 입력으로 전달하거나 파일을 읽도록 지시한다. 전체 대화 이력·폐기한 설계·코드 전문을 붙이지 않는다. 확정된 결정과 이유를 요약하고, 필요한 코드·프로젝트 지침은 작업자가 접근 가능한 경로로 지정해 직접 읽게 한다. 접근할 수 없는 필수 맥락만 관련 부분을 발췌한다.

작업 지시서는 다음 구조를 기본으로 한다.

```text
[목표] 기대하는 최종 동작
[확정 설계] 구현 방향, 주요 결정과 이유
[범위] 작업 디렉터리, 기준 git 상태, 수정 허용·제외 범위
[참조] 읽을 프로젝트 지침과 관련 파일 경로
[완료 기준] 기대 동작·예외 처리·검증 명령과 통과 기준
[실행] 직접 구현 → 테스트 → 수정 → 재검증. 중요한 설계 모호성만 에스컬레이션
[인계] 상태, 변경 요약·파일, 검증 결과·증거 경로, 미해결 사항
```

## 실행 로그와 세션 관리

- 실행별 고유 로그 파일에 stdout의 NDJSON 이벤트 스트림과 stderr를 저장한다. 전체 스트림이나 테스트 출력을 메인 컨텍스트에 그대로 반환하지 않는다. 저장은 셸 리다이렉션이나 실행 도구로 처리하고, 모델이 모든 이벤트를 읽은 뒤 요약하는 방식은 피한다.
- 진행 확인은 프로세스 상태·최근 작업 단계·차단 여부만 짧게 조회한다. 변화 없는 반복 조회와 전체 로그 재열람을 피한다. 사용자에게는 필요한 진행 상황을 계속 알린다.
- 완료 후 마지막 `type: result` 레코드에서 `subtype`, `sessionId`, `stopReason`, `usage`, `durationMs`, `finalText`를 추출한다. 선택 필드의 누락을 처리하고 종료 코드도 함께 확인한다. 실패 시 진단에 필요한 오류 부분만 추가로 읽는다.
- 작업 디렉터리·기준 git 상태·수정 범위·로그 경로를 작업별로 기록하고, CLI가 실제로 반환한 `sessionId`를 그대로 기록한다. 작업자가 CLI 반환 전에 `sessionId`를 만들어내거나 알고 있다고 가정하지 않는다.
- 같은 기능의 후속 수정은 컨텍스트가 여전히 유효하면 `cmd -p --resume <sessionId>`로 해당 세션을 재개하고 새 발견 사항·결정·수락 기준만 전달한다. 설계가 크게 바뀌었거나 세션 컨텍스트가 오래됐거나 신뢰할 수 없으면 재개하지 않고 현재 상태를 정리한 간결한 핸드오프로 새 세션을 만든다. 재개 시에도 적용되는 모델·effort·권한 설정을 유지한다.
- 여러 작업이 섞일 수 있는 `--continue`에 의존하지 않는다. 세션이 없거나 손상됐거나 무관한 새 작업이면 새 세션을 만들고 필요한 맥락만 다시 전달한다. 세션 재개가 공급자 캐시 히트를 보장한다고 설명하지 않는다.
- 중요한 설계 모호성으로 실행이 끝나면 차단 사유와 선택지를 받아 메인 모델이 결정하고 같은 세션에 결정 내용을 전달해 재개한다. 일반적인 테스트 실패와 구현 수정은 작업자가 내부에서 해결한다.

## 작업자 자체 완료 절차

1. 구현 후 스스로 diff를 검토하고 요구사항 충족, 누락, 회귀 가능성을 확인한다.
2. 변경에 맞는 검증을 직접 실행한다. 실패나 결함이 있으면 스스로 수정하고 관련 검증을 다시 실행한다.
3. 완료 기준을 만족하고 해결 가능한 결함을 처리할 때까지 구현 → 검증 → 수정 → 재검증을 내부적으로 반복한다. 첫 구현 직후 메인 모델에 검사를 요청하거나 중간 결과를 최종 결과로 반환하지 않는다.
4. 최종 diff와 실제 검증 결과를 확인한 뒤에만 최종 결과를 인계한다. 통과한 동일 검증을 이유 없이 무한 반복하지 않는다.
5. 인증·사용 한도·모델 미지원·권한 차단·필수 정보 부족·외부 환경 장애 또는 턴 한도로 완료할 수 없으면 `BLOCKED` 또는 `INCOMPLETE`로 보고한다. 권한을 우회하거나 실행하지 못한 검증을 통과했다고 하지 않는다.

최종 응답에는 다음을 포함한다.

- 상태: `READY_FOR_REVIEW`, `BLOCKED`, `INCOMPLETE` 중 하나.
- 변경 내용과 수정 파일, 완료 기준 충족 여부.
- 실행한 검증 명령과 실제 종료 코드·결과, 수정 후 재검증 결과, 증거 로그 경로.
- 남은 제약·미해결 항목. 없으면 없다고 명시한다.

최종 보고는 위 내용을 판단할 수 있는 짧은 요약으로 작성한다. 전체 diff·코드·도구 호출 이력·성공 테스트 로그는 붙이지 않고 파일 경로를 제공한다. 검증 명령·종료 코드·결과 요약과 증거 로그 경로는 남긴다. 중요 실패나 한계는 요약 길이를 줄이기 위해 누락하지 않는다. 메인 모델은 실제 변경과 증거를 별도로 확인한다.

## 메인 모델 인수 검증

- 실행 중에는 진행 상태를 파악하되 중간 산출물을 최종 코드 리뷰 대상으로 삼지 않는다. 사용자의 방향 수정이나 범위 이탈 등 개입이 필요한 경우는 즉시 조정한다.
- JSON 출력은 이벤트 스트림과 마지막 결과 행으로 구성된다. 프로세스 종료만으로 성공을 판단하지 않고 최종 상태·종료 코드·검증 증거를 확인한다. 턴 한도 도달(exit 8)은 미완료다.
- `READY_FOR_REVIEW` 결과를 받은 뒤 실제 diff와 검증 증거를 독립 검토한다. 최종 수락 판단에 꼭 필요한 결정적 확인 실행은 메인 모델이 직접 할 수 있지만, 작업자의 전체 검사 세트를 상시 중복 실행하지 않는다. 추가 개발 검증은 검증 방법을 지정해 작업자에게 실행시키고 실제 결과를 확인한다. 작업자의 완료 주장만으로 작업을 종료하지 않는다.
- 최종 검증에서 발견한 모든 후속 코드 수정과 그에 따른 테스트·재검증은 발견 사항과 수락 기준을 전달해 다시 작업자에게 맡긴다. 메인 모델이 코드를 직접 고치지 않는다. 작업자는 동일한 자체 검증·수정 절차를 거친 뒤 최종 결과를 다시 인계한다.
- 도메인별 리뷰 스킬의 필수 리뷰 절차는 그대로 수행한다. 작업자의 자체 검증이 메인 모델의 최종 검증이나 필수 리뷰를 대체하지 않는다.
- 메인은 최종 diff와 판단에 필요한 주변 코드·검증 증거를 직접 확인한다. 작업자가 탐색한 모든 파일을 다시 읽거나 개발 과정을 재현하지 않는다. 위험·불일치가 발견되면 필요한 범위로 검토를 확대한다. 토큰 절약을 이유로 중요한 검증을 생략하지 않는다.
- 작업자의 토큰 사용량과 Codex 메인 사용량은 구분해 보고한다. `usage`가 없으면 알 수 없음(unknown)으로 표시하고 추정하지 않는다. 작업자 캐시 비율을 메인 토큰 절감률로 해석하거나, 비교 측정 없이 절감률을 주장하지 않는다. 목표는 중간 로그 유입과 중복 구현·개발 검증을 줄이는 것이다.
- 비용·시간·재작업 횟수는 실제로 측정된 경우에만 보고하고, 측정하지 않은 수치를 만들어내지 않는다.
- 인증 실패·사용 한도·모델 미지원·권한 차단 등으로 위임할 수 없으면 원인을 알린다. 권한을 우회하거나 다른 유료 모델·추가 크레딧으로 자동 전환하지 않는다. 메인 모델이 구현을 대신해야 한다면 사용자에게 역할 변경을 확인한다.
